# מדריך שלבים: כתיבת מאמר בלוג חדש

מסמך תפעול לליין "משימת התוכן היומית" (ראו `CLAUDE.md` וסעיף הליינים). מיועד לכל מי שכותב מאמר חדש לאתר, בין אם סשן Claude ובין אם בן אדם. השלבים בסדר שבו הם קורים בפועל.

## 0. לפני שכותבים

1. `git fetch origin main` והתחל ממנו. אל תבנה על ענף בן כמה שעות.
2. הצץ ב-PR-ים פתוחים ובקומיטים של היום האחרון על `main`. אם מישהו כבר בתוך אותו קובץ או אותו נושא, אל תתחיל גרסה שנייה.
3. פתח את `docs/seo-content-roadmap.md`, מצא את הנושא הבא בתור לפי סדר העדיפות, וסמן אותו כתפוס (הוסף `V` בתחילת השורה) **ברגע שמתחילים**, לא כשמסיימים. שורה לא מסומנת היא הזמנה לסשן שני לכתוב את אותו מאמר.
4. ודא שהנושא לא מכוסה כבר: חפש ב-`src/lib/blogMeta.ts`, `src/lib/blogPosts.ts` ו-`t.data.articles` (בתוך `src/lib/strings.ts`). הבנייה נכשלת על שני מאמרים שכותרותיהם וריאציות זו על זו ועל שני עמודים עם אותו תיאור מטא, אבל בדיקה לפני הכתיבה זולה מגילוי אחרי.

## 1. מיצוב: שני תחומים בלבד

לפי `CLAUDE.md`, כל מאמר חדש חייב לשרת אחד משני התחומים: **נדל"ן והתחדשות עירונית** (בארץ ובחו"ל), או **AI** (ייעוץ, ליווי והדרכות, לא רק חוות דעת). **אל תכתבו מאמר גישור חדש** תחת אף נסיבות; אשכול הגישור מלא (64 מאמרים, תקרה קבועה) והבנייה נכשלת אם הוא גדל.

## 2. אימות מקורות (הכלל הקבוע החמור ביותר)

לפני שכותבים משפט אחד שמכיל פסיקה, סעיף חוק, הוראת רגולטור, תאריך תחילת תוקף, סכום קנס או סף כלשהו: **חובה לאמת מול הטקסט המקורי עצמו, משני מקורות בלתי תלויים**. פרשנות, ולו מומחית, היא לכל היותר חיזוק ואינדיקציה למקור, לעולם לא הבסיס עצמו. כתבה עיתונאית חלשה עוד יותר.

- שני המקורות חייבים להסכים על מספר ההליך, הערכאה, התאריך, ההרכב והתוצאה.
- אל תשלימו הרכב, תאריך מדויק או עובדות בהיסק. `dateLabel` אומר מה שידוע (`9.12.2025` או `דצמבר 2025` בלבד) ולא מעבר לכך.
- הפרידו בין מה שהוכרע לבין מה שנאמר סביב זה. אמרות אגב, או פסיקה שניתנה במישור העקרוני בלבד אחרי שהסכסוך התיישב, אינן הלכה מחייבת, והצגתן ככזו היא כשל בפני עצמו.
- אם האימות לא הושלם: **המאמר ממתין**. כרטיס חסר הוא פער; כרטיס עם אסמכתא שאיש לא פתח הוא הכשל עצמו, שהמשרד כותב עליו על העמוד שלו.
- אם מדובר בפסיקה, הרשומה חייבת לשבת ב-`lalum-app/src/data/rulings.json` (הטיפוסים אוכפים שדות חובה: אסמכתא, ערכאה, תאריך, מקור פומבי) והמאמר מפנה אליה, לא כותב את הציטוט בעצמו.

## 3. כתיבת המאמר: שני קבצים, מפתח משותף

מאמרי הבלוג (בשונה מהתוכן המוצג ב-`t.data.articles`) חיים בשני קבצים תחת `lalum-app/src/lib/`, שניהם נערכים ידנית ומקושרים באותו `slug`:

### 3.1 `blogMeta.ts`, המטא-דאטה

הוסיפו רשומה לתחילת (או במקום המתאים ב-) המערך `blogMeta`:

```ts
{
  "slug": "example-article-slug",
  "title": "כותרת המאמר בעברית",
  "excerpt": "תקציר של משפט עד שניים, בדיוק מה שמופיע בכרטיס ובתיאור המטא.",
  "date": "ספטמבר 2026",
  "cover": "/images/covers/example-article-slug.webp"
}
```

- `slug`: אנגלית עם מקפים למאמרים בנושאי AI/רגולציה; עברית עם מקפים מקובלת למאמרי נדל"ן/מגזריים ותיקים יותר (ראו את שני הסגנונות הקיימים בקובץ). היו עקביים עם הסביבה שאתם כותבים אליה.
- `title`: ייחודית, לא וריאציה על כותרת קיימת (בדיקה 7 בבנייה).
- `excerpt`: הופך גם לתיאור המטא של הדף. חייב להיות ייחודי מול **כל** תיאור מטא אחר באתר (בדיקה 8).
- `cover`: קובץ תחת `public/images/covers/`. אם אין תמונה זמינה, אפשר להצביע על תמונה קיימת רלוונטית זמנית, אבל עדיף SVG/WEBP ייעודי.

### 3.2 `blogPosts.ts`, הגוף

הוסיפו ל-`bodies` (המפתח `Record<string, string>`) רשומה עם אותו `slug` בדיוק, וגוף המאמר כמחרוזת template literal אחת (פסקאות מופרדות בשורה ריקה, `\n\n`):

```ts
"example-article-slug": `הפסקה הראשונה...

הפסקה השנייה...`,
```

**חשוב:** אל תפצלו את הגוף למערך של פסקאות בודדות ואל "תאטרו" מחרוזת. בדיקה 1 בבנייה (`no single-character paragraphs`) קיימת בדיוק כי מחרוזת שרוצתה כאילו הייתה רשימת פסקאות הגיעה פעם לפרודקשן ככה.

## 4. כללי עברית וטיפוגרפיה (מ-CLAUDE.md, PERMANENT)

- **אין מקפים כסימן פיסוק.** לא `—`, לא `–`, ולא `-` כמפריד משפטים/סעיפים. השתמשו בפסיק, נקודה, נקודתיים או סוגריים. מקף שהוא חלק אינטגרלי ממילה, מונח, תאריך, כתובת או אימייל (`פינוי-בינוי`, `תמ"א 38`, `2026-06-22`) נשאר כמות שהוא.
- **גרשיים תקניים**, לא גרש ASCII כפול, בראשי תיבות עבריים (`תמ"א`, `בג"ץ`, `עו"ד`). בדיקה 11 בבנייה אוכפת זאת.
- **השם**: תמיד `ד״ר עו״ד אברהם ללום` (בסדר הזה) באזכור מלא ראשון; `ד״ר ללום` באזכורים הבאים באותו מאמר. לעולם לא `ד״ר אברהם ללום` או `עו״ד אברהם ללום` לבד. בדיקה 9 בבנייה אוכפת זאת.
- **טוקנים לטיניים/טכניים** (כתובות, מונחים באנגלית, קודי חוק כמו `EU AI Act`) בתוך טקסט עברי: אם יש סיכוי לבעיית כיווניות (RTL/LTR מעורב), עטפו ב-`<span dir="ltr">` בכל מקום שהתצוגה בפועל דורשת זאת (רלוונטי בעיקר לרכיבים סטטיים/PDF, פחות לטקסט מאמר רגיל שרץ דרך `LangContext`).

## 5. אחרי הכתיבה: מחוללים ובדיקות, בסדר הזה

```bash
cd lalum-app
npm run split-articles   # מחדש src/data/articleIndex.json ו-src/data/posts/<slug>.ts
                          # (נושא + שלושה מאמרים "קרובים", מחושבים אוטומטית)
rm -rf dist && npm run build   # tsc + vite build + 16 בדיקות build-check אוטומטיות
npm run seo-check         # 27 בדיקות SEO/GEO, כולל sitemap ו-llms.txt
npm run faq-check         # 15 בדיקות מבנה נתונים מובנה
npm run lint               # ESLint, אמור להישאר על הבסיס הקיים (0 שגיאות)
```

**אין לדלג על `split-articles`.** זו בדיוק הסיבה לבדיקה 16 ("every article carries its topic and neighbours"): מאמר שנוסף בלי להריץ אותה יגיע ל-`main` בלי נושא וקישורי המשך, ובנייה עתידית (אולי של סשן אחר) תיכשל על כך. אם `npm run build` נכשל על משהו לא קשור למאמר שכתבתם (למשל בדיקה 16 בגלל מאמר אחר שנוסף במקביל), הריצו `npm run split-articles` מחדש.

בדיקות build-check הרלוונטיות למאמר (16 בסך הכול, כל הרשימה ב-`npm run build`):
- אין פסקה בת תו אחד (מחרוזת גוף שנוצרה נכון).
- כל מסמך שנוגע לאינדוקס יש לו תוכן ממשי.
- ה-sitemap פותר את כל ה-URL-ים, כולל hreflang.
- שני מאמרים לא מתחרים על אותה שאילתה (כותרות/excerpt ייחודיים).
- כל תיאור מטא ייחודי בכל האתר.
- צורת השם הקנונית בלבד.
- כל עמוד מקושר לשני תחומי הליבה.
- אשכול הגישור לא גדל מעבר ל-64.
- גרשיים תקניים בראשי תיבות.
- Structured data (JSON-LD) תקין, וכל מאמר נושא סימון `BlogPosting`.
- כל מאמר נושא נושא וקישורי המשך (בדיקה 16, תלויה ב-`split-articles`).

## 6. אם המאמר מזכיר PDF/חוברת להורדה, כלי אבחון, או רובריקת מגזר

אלה נגזרים ישירות ממבנים קיימים (`src/lib/sectors.ts`, `src/lib/legalTools.ts`, `vite.config.ts`'s `sectorBookletHtml`/`toolBookletHtml`). לא יוצרים HTML/PDF חדש ידנית: מוסיפים לאובייקט הנתונים, והבנייה מייצרת הכול ממנו (כולל בדיקת ה-RTL/bidi בברוקלט). אם זה לא רלוונטי למאמר שלכם, דלגו על השלב הזה.

## 7. גיט, PR, ומיזוג

לפי `CLAUDE.md`:

1. **לעולם לא לדחוף ישירות ל-`main`.** חוק ברפו אוכף PR, וגם אוטומציה שמנסה לדחוף נדחית.
2. `git checkout -b claude/<תיאור-קצר>` מתוך `main` טרי (אחרי `git fetch`).
3. קומיט אחד, עם הודעה שמסבירה *למה*, לא רק *מה*. מסיים בשורות הייחוס שמופיעות ב-system reminder של הסשן (Co-Authored-By / Claude-Session).
4. `git push -u origin <branch>`.
5. פתחו PR **כטיוטה** קודם. בדקו סטטוס CI (Vercel), ורק כשהוא ירוק הפכו אותו ל-ready והמזגו (אם אתם הסשן שאמון על כך).
6. **נושא אחד ל-PR אחד**, ממוזג באותו סשן. ענף שחי יום שלם אוסף התנגשויות.
7. חזרו ל-`docs/seo-content-roadmap.md` וודאו שה-`V` שסימנתם בשלב 0 עדיין שם (הוא כבר שם, זו רק בדיקת שפיות אחרי מיזוג).

## מה **לא** לעשות

- לא לכתוב מאמר גישור חדש, ולא "לתייג" מאמר שנועד לאחד משני התחומים כגישור רק כי הוא מזכיר אותו כאמצעי פתרון.
- לא לפרסם פסיקה/חקיקה/סף כספי בלי אימות כפול מהמקור.
- לא לגעת ב-`src/data/articleIndex.json` או ב-`src/data/posts/*.ts` ידנית: אלה קבצים מחוללים, `split-articles` דורסת אותם בכל הרצה.
- לא לפצל את גוף המאמר למערך פסקאות.
- לא לדחוף ל-`main` ישירות, ולא למזג PR שנוגע גם במאמר וגם בנושא לא קשור (עיצוב, נגישות, תשתית).
